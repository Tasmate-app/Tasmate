# 開発ロードマップと未決定事項

## 1. 推奨する開発段階

### Phase 0：仕様の最小確定

- 対象プラットフォームを決める。
- タスク、タイマー、完了の最小仕様を決める。
- 作業時間からゲーム内進行量を計算するルールを決める。
- AI 報酬決定の入力・出力と上限を定義する。
- 保存方式と最低限のデータモデルを決める。

### Phase 1：基本ループの試作

- タスク作成とタイマー
- タスク完了記録
- 戦闘先選択
- 作業時間に応じた素材収集
- 施設の基本生産
- 通貨・素材の所持表示
- キャラクターの簡易レベルアップ
- データ保存

### Phase 2：報酬とバランスの改善

- AI 報酬決定の統合
- 報酬理由の表示
- 上限・検証・フォールバック処理
- 中断・再開の運用改善（中断中一覧の通知・上限など）
- 報酬・生産量・強化コストのバランス調整

### Phase 3：拠点の魅力を強化

- シェアハウス画面の改善
- 家具の購入・配置
- 施設の見た目や強化演出
- キャラクターの滞在・行動演出
- コスチューム

### Phase 4：長期的なコンテンツ

- キャラクターとの交流
- プレゼント合成
- 趣味時間とゲーム内効果
- 追加の戦闘先・素材・施設
- より多様なキャラクター育成

## 2. 優先して決めるべき質問

### タスク・タイマー

- タスクを完了扱いにする条件は何か。
- タイマーの開始・停止・一時停止・中断の基本仕様は実装済み（中断時は0.5倍で確定、再開後は再開分のみ報酬）。中断中一覧の通知方法は検討中。
- 予定時間を超えて作業した場合、報酬や収集量はどうなるか。
- 複数タスクを同時に進行できるか。
- タイマー中にアプリを閉じても進行を維持するか。

### AI 報酬

- AI は報酬の種類まで決めるのか、量だけを決めるのか。
- タスク内容・科目・難易度をどう評価するか。
- 日次上限や報酬の最低値・最大値を設けるか。
- 報酬の理由を表示するか。
- AI が利用できない場合、固定ルールに切り替えるか。
- タスクの説明に個人情報が含まれる場合、何を AI に送信するか。

### 戦闘・キャラクター

- 戦闘は完全自動か、選択・操作要素を含むか。
- 1回の作業セッションで何人派遣できるか。
- 属性は何種類にするか。
- 相性倍率をどの程度にするか。
- キャラクターのレベルはどのように収集効率へ影響するか。

### 施設・経済

- 施設は同時に何個稼働できるか。
- 生産は作業時間に比例するか、一定時間ごとの区切りで発生するか。
- 生産物や素材の保管上限を設けるか。
- 施設強化のコストと効果をどう決めるか。
- 通貨と素材の種類をどこまで細分化するか。

### 拠点・趣味時間

- 家具は自由配置か、決められたスロットに配置する方式か。
- キャラクターは拠点内を動き回るか、定位置で過ごすか。
- 趣味時間は現実の時間管理にも関わるか、ゲーム内の解禁要素か。
- 趣味時間の効果が、休息を取らないことへの圧力にならないようどう設計するか。

### 技術・運用

- Web、PC、スマートフォンのどれを最初の対象にするか。
- ローカル保存とクラウド保存のどちらを採用するか。
- ログインや端末間同期は必要か。
- AI サービスの料金・速度・プライバシー要件をどう扱うか。
- データのエクスポート・削除をどのように提供するか。

## 3. リスクと対策の方向性

| リスク | 対策の方向性 |
|---|---|
| AI 報酬が毎回ばらつく | 入力・出力を構造化し、アプリ側で上限と検証を行う |
| タスク内容を誇張すると報酬が増える | 報酬上限、入力ルール、完了記録を組み合わせる |
| タイマーだけ動かして報酬を得る | 完了確認や合理的な上限を検討する。ただし監視を過度に強制しない |
| 報酬が増えすぎて経済が崩れる | 生産量、強化コスト、報酬量をまとめて調整する |
| 予定どおりにできないと継続が苦痛になる | 失敗時の重い罰を避け、再開しやすい仕組みにする |
| ゲームが現実の休息を妨げる | 休息を損失として扱わず、趣味や休息を尊重する |

## 4. MVP で検証する仮説

- ゲーム内の進行が、タスクを始めるきっかけになる。
- 作業中にキャラクターや施設が進行することが、作業継続の楽しさにつながる。
- 報酬量と報酬理由に納得感がある。
- キャラクターや施設を強化したいという目標が次の行動につながる。
- 失敗や中断があっても、プレイヤーが再開しやすい。
