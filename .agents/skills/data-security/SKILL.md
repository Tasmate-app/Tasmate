# Data and Security

## データ設計
- 初期開発ではローカル保存を利用し、必要な段階でSupabase・PostgreSQL・Supabase Auth・RLS・Edge Functionsを導入する。
- UIコンポーネントから保存先やデータベースの詳細に直接依存させない。
- データの取得・保存はサービス層を経由させる。
- ローカル保存からSupabaseへ移行する際に画面全体を書き換えずに済む構造を目指す。
- 将来の複数ユーザー対応を考慮し、ユーザー所有データを明確にする。

## セキュリティ
- ユーザー所有データには必要に応じて `user_id` を持たせる。
- オンライン環境では認証だけでなく、データ単位の認可を実装する。
- Supabaseでは必要なテーブルにRLSを設定し、ポリシーをテストする。
- サービスロールキー、APIキー、パスワードなどの秘密情報をソースコードへ記述しない。
- ブラウザに公開してよい環境変数と、サーバー側だけで使う秘密情報を区別する。
- `.env` などの秘密情報をGitへコミットしない。
- `.env.example` には値ではなく必要な変数名と説明を記載する。
- SQLや外部入力を扱う際は権限と入力検証を考慮する。

## データ変更
- データベース変更はマイグレーションで管理する。
- 既存データを破壊する操作は、明示的な必要性を確認する。
- 外部入力、APIレスポンス、保存データは必要に応じて実行時検証する。
- ユーザーの作業記録や個人情報を外部サービスへ送る場合、送信内容を最小限にする。
